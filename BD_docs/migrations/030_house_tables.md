# Миграция 030: столы-домики (кирпичная метка номера стола)

## Дата выполнения
2026-08-15

## Файл
`server/migrations/030_house_tables.sql`

## Что делает
```sql
ALTER TABLE slicer_settings
  ADD COLUMN IF NOT EXISTS house_tables INTEGER[] NOT NULL DEFAULT '{30,31,32}'::integer[];

ALTER TABLE slicer_settings
  DROP CONSTRAINT IF EXISTS slicer_settings_house_tables_sane;
ALTER TABLE slicer_settings
  ADD CONSTRAINT slicer_settings_house_tables_sane
  CHECK (
    COALESCE(array_length(house_tables, 1), 0) <= 100
    AND array_position(house_tables, NULL::integer) IS NULL
  );
```
Добавляет в singleton-таблицу настроек список номеров столов-домиков.
`IF NOT EXISTS` + `DROP CONSTRAINT IF EXISTS` — миграция идемпотентна,
повторный запуск безопасен.

**Чужие таблицы не затрагиваются.**

## Зачем
Часть посадки ресторана — отдельные домики на улице (столы 30, 31, 32).
Блюда для них уносят не в зал, и нарезчику важно видеть это ещё при нарезке.
На доске все номера столов выглядели одинаково (жёлтые), домик от обычного
стола отличить было нельзя. Список номеров вынесен в настройки, чтобы при
изменении рассадки не править код.

## Почему массив в настройках, а не отдельная таблица
Это ровно список чисел без собственных атрибутов; он живёт вместе с
остальными тумблерами доски и читается тем же `GET /api/settings`, который
фронт и так грузит при старте. Отдельная таблица потребовала бы своего
роута, поллинга и CRUD-экрана ради списка из трёх чисел.

## Почему DEFAULT именно `{30,31,32}`
Боевая рассадка ресторана на дату миграции — модуль работает «из коробки»
и на чистой установке, и после восстановления дампа данных (в
`COPY public.slicer_settings (...)` внутри `slicer_data_dump.sql` этой
колонки нет, поэтому подставится DEFAULT). Значение не является частью
логики: любой номер добавляется и убирается в UI.

## Как выглядит (логика на фронте, БД хранит только список)
- `components/ui/HouseTableBadge.tsx` — номер стола рисуется кирпичным
  (`#E2725B`) внутри SVG-контура домика (стены + двускатная крыша).
  `preserveAspectRatio="none"` растягивает домик под ширину номера,
  `vector-effect="non-scaling-stroke"` держит толщину линии постоянной.
- Компонент общий для доски (`OrderCard`) и админки (`SystemSettingsTab`):
  владелец настраивает список и сразу видит то, что увидит нарезчик.
- Кирпичный тон осветлён относительно «настоящего» кирпича (#B22222): на
  тёмном фоне карточки (#151d2c) тот даёт контраст ~2.9:1 и не читается
  с трёх метров.

## Область действия метки (решение владельца)
Метится **только номер стола**. Рамка карточки (ULTRA / VIP / клейм
«В работе»), мини-ряд разморозки, панель парковки и история заказов
не меняются.

## Совмещение с парковкой
Фиолетовая рамка вокруг номера — другая метка («стол парковался в течение
смены»). Домик её не отменяет: форма и обводка кирпичные, а заливка и цвет
цифры внутри остаются фиолетовыми.

## Валидация
| Слой | Что проверяет |
|---|---|
| CHECK (030) | ≤ 100 элементов, без NULL внутри массива |
| `PUT /api/settings` | массив целых 1..9999, ≤ 100 шт.; дедуп + сортировка по возрастанию |
| UI | те же границы + понятное сообщение под полем ввода |

## Попутно исправлено
`PUT /api/settings` падал 500-кой на **любой** настройке: после правки
килсвитча синхронизации (ревью 2026-08-14) параметр `$10` остался в массиве
значений, но исчез из текста запроса, и Postgres отвечал «не удалось
определить тип данных параметра $10». Админка молча откатывала изменение и
перечитывала старые значения из БД. Нумерация параметров сделана сплошной
($1..$18), плейсхолдер убран.

## Откат
```sql

ALTER TABLE slicer_settings DROP COLUMN IF EXISTS house_tables;
```
